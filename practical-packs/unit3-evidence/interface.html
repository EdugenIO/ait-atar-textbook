Annotate, test and revise a festival interface

Unit 3 · fictional community-festival client brief. Read the chapter explanation first. These are worked decisions, not observed learner results.

Worked decisions

FocusDecision and explanation
Task and hierarchyA visitor must find the 10:00 printmaking session and its room. Programme → Session details gives a labelled path; the reference has a visible return route. A hierarchy describes relationships rather than only a list of pages.
Element → principle → effectThe larger, darker session heading uses size and tone to create emphasis. Space groups time and venue by proximity; a repeated heading treatment supports unity. The intended result is easier scanning, which still needs a task observation.
GUI and helpThe reference uses labelled links and expandable help beside the programme. A touchscreen kiosk may need different target spacing from a desktop. Help describes what a visitor can do; an icon alone may be ambiguous.
Usability, inclusion, accessibilityTask success and effort address usability. Keyboard operation and meaningful text are accessibility checks. An offline printed route and plain language can reduce participation barriers. These questions overlap but are not interchangeable.
Critical analysisA decorative label may appear balanced while obscuring a caption. Preserve the required information, revise its placement, then compare the same task in the revised version. A claimed principle does not prove an effective outcome.

Check your reasoning

A visitor likes the colours but cannot find the room. Has the task passed?

Compare your explanation

No. Preference is one response; the room-finding task failed. Investigate grouping, labels and help, revise the cause and repeat that task.

Production sequence

  1. Copy the supplied festival.html and festival.css into your own folder. Open the unchanged reference and complete the session-finding task.
  2. Draw a revised layout and annotate at least three choices with element, principle, intended task effect and a possible drawback. Create a site map with return routes.
  3. Implement your changed venue/access need using labelled navigation and relevant help. Keep content order logical without relying on colour alone.
  4. Test keyboard-only navigation, visible focus, 200% text enlargement and a narrow/wide viewport. Record the actual environment and task result.
  5. Identify one problem, revise the source and repeat the same check. Explain whether the evidence supports your intended design effect.

Apply independently

Complete the production sequence using your own version of the festival brief. Change the venue and one user access need, then justify and test the resulting revision. Retain your own outputs and observations; the supplied reference is a model.

Use this within the existing chapter task, not an extra assessed project or additional teaching week. Record expected and actual results separately.

Evidence to retain

  • Annotated before/after design and hierarchy map.
  • Source copies, expected/actual observations, revision and retest.
  • State which users and access methods were not tested.

Actual learner performance, native application output and independent teacher review remain unverified. Supplied model results must not be copied into an observed-result log.
