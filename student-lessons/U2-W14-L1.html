2. Understand the lesson ideas

A project plan helps a team turn a business problem into a useful solution. Decide what matters, organise the work and check the result against the client’s requirements.

Agree the scope and requirements

A small prototype could include service information, fictional hours and contact instructions. A real booking system with payments is a different scope. Record what is included and what is excluded so the team can plan sensibly. For each requirement, specify evidence: “A visitor can find the opening hours from Home” can be checked with a navigation task. Record unresolved questions rather than treating guesses as facts.

Put tasks in a useful order

Break the work into small tasks: confirm content, map destinations, draft layouts, create assets, build, test, revise and prepare a handover. Mark dependencies. The final hours cannot be approved before the client confirms them, but rough layout alternatives can use labelled placeholders while waiting. Identify who is responsible and who reviews each task.

Explore this concept and its visual/example support

Manage time through checkpoints

Choose a small milestone, such as a working navigation draft, before polishing every graphic. Use a task list, calendar or board to show priorities and progress. Leave time for testing and revision. If a required asset is delayed, move to a task that can proceed, reduce optional decoration or agree a revised scope. Do not remove an essential access or privacy check merely to make the schedule look complete.

Language you can use in your explanation
Requirement
A condition or capability a proposed solution must meet.
Action plan
An organised record of tasks, responsibilities, resources and timing.
Dependency
A relationship in which one task needs another task or resource before it can proceed.
Milestone
A significant checkpoint used to review project progress.
Resource
Something needed for the work, such as time, people, tools, information or approved assets.
Scope
The agreed boundaries of what a project will deliver.

3. Follow a worked decision

A fictional bicycle shop needs a small communication solution, managed files and a justified LAN proposal. Staff and customers have different access needs. Use disposable working copies and invented customer information.

Today’s decision in that case

Recheck scope, dependencies and resources before building. A date passing does not establish a prerequisite is complete.

  1. Identify: Which requirement, concept or distinction does this decision address?
  2. Explain: Which part of the reasoning supports the decision?
  3. Qualify: What condition or evidence would you need before claiming it works in practice?

The decision is a supplied teaching model. Its proposed checks are not your observed results.

Deeper chapter model: Replan when required content is delayed
  1. Requirement: Visitors must find accurate opening hours.
  2. Dependency: The client has not yet confirmed the hours, so the final wording cannot be approved.
  3. Work that can proceed: Build the navigation and compare layouts using a clearly labelled placeholder.
  4. Checkpoint: Review the working routes before polishing optional animation.
  5. Update: Replace the placeholder when the hours are confirmed and record the approval.
  6. Test and evaluate: Ask a visitor to locate the hours, check the displayed text and record any remaining limitation.

A plan can change while preserving the essential requirement. Activity alone is not proof that the project is ready.

Spot and correct a connected misconception

Claim to examine: Finishing every planned task proves the client’s problem is solved.

Compare the correction

Tasks can be completed while the product still fails a user need. Evaluate the delivered behaviour against the requirements.

Supported chapter question

An optional animation is unfinished, and testing reveals that the Services link is broken. Which should be prioritised, and why?

Check the supported reasoning

Repair and retest the required route first because it blocks a user task. Review the optional animation against the remaining time and agreed scope. Record the decision rather than silently changing the promise.

For example: a visitor can navigate from Home to the repair-service details and back using the provided links. State the intended context and how you will observe it.

Transfer and test the limits

Change one relevant client condition: audience/access need, output medium, available application, recovery need or resource limit. Explain which part of today’s decision still applies, which part changes and what new evidence you need. Choose a change that matters to this lesson rather than adding an unrelated feature.

Teaching choices and review limits

Use retrieval, explicit instruction, a worked decision, faded support, self-explanation, discussion, independent application, feedback and reflection in the core route. Optional error analysis, interleaving and transfer can replace practice when appropriate. For a learner needing support, narrow the task and retain one scaffold; for a learner ready for challenge, remove the scaffold or vary a meaningful condition. No new accounts, real personal data or purchases are required.

The lesson uses selected chapter readings and a distinct scheduled-task model. Native application operation, approved online collection, representative access trials and independent subject review are not established by the supplied text. Formal assessment follows the school’s approved conditions.
