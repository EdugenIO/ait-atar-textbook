Visual walkthrough

Trace the files needed for recovery

Pause and predict: I1 is missing. Which illustrated route still has its required backup set?

Try a small change: The failure occurs after new Wednesday edits but before the next backup. What is not protected by Tuesday’s recovery point?

Worked example · Recover a Wednesday booking list

  1. Sunday: Make full backup F of the selected booking data.

    Why this matters: Read each backup’s reference point before selecting a restore sequence.

  2. Monday: Record changes A and complete backup I1 in the incremental scheme, or D1 in the differential scheme.
  3. Tuesday: Record new changes B and complete I2, or D2. D2 includes changes since Sunday.
  4. Wednesday failure: The computer fails before another backup. The latest available recovery point is Tuesday’s completed backup.
  5. Incremental restore: Use F → I1 → I2 in order. This simple chain needs both increments.
  6. Differential restore: Use F → D2. D1 is not required for this recovery point.
  7. Check: Open sample bookings, check expected records and report any work after the recovery point as potentially lost.

    Why this matters: A complete-looking schedule still needs usable copies and a successful recovery check.

These are alternative backup schemes, not instructions to mix both chains. The example assumes successful, usable backups and a supported restore process.

2. Publishing reliable and accessible web information

Recall

  • What is the difference between a claim and evidence that supports it?
  • Why should a plan include checks as well as production tasks?

Visual walkthrough

Follow a value through the validation checks

Pause and predict: Why should the server reject 21 even if the browser should have blocked it?

Try a small change: The allowed maximum becomes 30. Which tests should change?

Worked example · Test a fictional group-size field

  1. Rule: The field is required and must contain a whole number from 1 to 20 inclusive.

    Why this matters: Explicit rules determine expected results before testing.

  2. Empty: Reject: explain that a group size is required.
  3. 0 or 21: Reject: explain the allowed range.
  4. 1 and 20: Accept under this field’s rules: both boundaries are included.
  5. 2.5 or letters: Reject: request a whole number in the allowed range.
  6. Server check: A real collection service must repeat the rules on the server. A browser message alone cannot secure submitted data.
  7. Limit: An accepted number does not prove that this many people will actually attend.

    Why this matters: Keep validation behaviour separate from truthfulness, identity and permission.

Test valid, invalid and boundary cases. Explain what each test establishes and what it leaves unknown.
